### 2.12 验证后的关闭与清理（启动的逆操作）

验证完要关干净——分两层：**应用服务**（6 个 node 进程）和**基础设施容器**（3 个 docker 容器）。

#### ① 关应用服务（占 3000/3001/4000-4003 端口）

```bash
# 情况 A：前台 pnpm dev 启动的 → 在该终端按 Ctrl+C（turbo 连带停掉全部子进程）

# 情况 B：nohup / 后台方式启动的，或 Ctrl+C 后仍有残留 → 按端口找 PID 精确清理：
ss -ltnp | grep -E ':(300[01]|400[0-3])\s'   # 列出占用进程，看 users:(("node",pid=NNNN,fd=..))
kill -9 <pid> <pid> ...                       # 逐个杀掉

# 复查（通过标准：无任何输出）
ss -ltn | grep -E ':(300[01]|400[0-3])\s'
```

> ⚠️ 不要用 `pkill -f "next dev"` 这类模糊匹配来停服务：模式字符串会匹配到执行命令的 shell 自己，把自己的终端一起杀掉（本机实测 exit 144）。认端口、认 PID 最稳。

#### ② 关基础设施容器（占 3306/6379/9092 端口）

```bash
# 日常关闭（推荐）：容器停止但保留，数据完整保留
docker compose -f infra/docker-compose.dev.yml stop
```

**注意：compose 里三个容器都配了 `restart: unless-stopped`**——意思是只要不是用 stop 命令停的（比如直接关 WSL/重启 Docker），它们会自己爬起来继续占端口。所以「下次开机不想让它们自动跑」就 `stop` 一次；「想让它随 WSL 启动自动就绪」则不用管。

#### ③ 关闭程度对照表（数据会不会丢）

| 命令 | 容器 | 数据（volume） | 适用场景 |
|---|---|---|---|
| `stop` | 停止，保留 | ✅ 保留 | 每天下班关机前 |
| `down` | 删除 | ✅ 保留（volume 独立于容器） | 想清掉容器定义重新 up |
| `down -v` | 删除 | ❌ **连数据一起删** | 彻底重置环境（慎用） |

#### ④ 验证真的关干净了

```bash
ss -ltn | grep -E ':(300[01]|400[0-3]|3306|6379|9092)\s' || echo "9 个端口全部已释放"
docker ps --format '{{.Names}}' | grep cex || echo "无 cex 容器在运行"
```


#### ⑥ 彻底重置（从零再来一遍）

```bash
docker compose -f infra/docker-compose.dev.yml down -v   # 删容器+删数据
docker compose -f infra/docker-compose.dev.yml up -d     # 重建容器（空库）

  GRANT ALL PRIVILEGES ON cex.* TO 'cex'@'%';
```

## 4. GitHub Actions CI：怎么证明这个 CI 文件没问题

> 你点名要的部分。背景：项目原先写的是 GitLab CI（`.gitlab-ci.yml`），**已删除**；现使用 `.github/workflows/ci.yml`，分三层验证，一层比一层接近真实。

CI 文件内容概要（`.github/workflows/ci.yml`）：触发条件 `push 到 main/develop` 或任意 `pull_request`；单个 job `verify` 跑在 `ubuntu-latest`；步骤 = checkout → pnpm（版本自动读根 package.json 的 `packageManager: pnpm@9.15.0`）→ Node 22（带 pnpm 缓存）→ `pnpm install --frozen-lockfile` → lint → typecheck → test → build。与本地 §2.6 四条命令完全一致，**本地绿 = CI 绿**，不会有"本地好好的 CI 挂了"这种环境差异。

### 第一层：静态校验（30 秒，push 前就该跑）

用 **actionlint**——GitHub Actions 生态的标准校验器，能查出：YAML 语法错误、非法字段名（如把 `runs-on` 写错）、step 里引用不存在的 input、shell 脚本低级错误。

```bash
# 安装（一次性；Docker Hub 拉镜像慢时的备选方案就是官方安装脚本）
curl -sL https://github.com/rhysd/actionlint/releases/download/v1.7.7/actionlint_1.7.7_linux_amd64.tar.gz | tar xz -C /tmp actionlint
# 校验
/tmp/actionlint .github/workflows/ci.yml
```

**通过标准：无任何输出 + exit 0。实测：v1.7.7 校验本仓库 ci.yml 通过 ✅**
（改过 ci.yml 之后必须重跑这一条。）

另一层保底：YAML 语法本身可以 `pnpm dlx js-yaml .github/workflows/ci.yml` 验证能被解析。

### 第二层：本地完整演练（可选，15 分钟）

用 [act](https://github.com/nektos/act) 在本地 Docker 里把整个 workflow 真跑一遍：

```bash
pnpm dlx @github-local/act -j verify      # 或 brew install act / 官方二进制
```

通过标准：`✔ Success - verify ...`。适合 CI 挂了但看不出来为什么的时候本地复现。注意 act 对 `actions/setup-node` 的缓存特性支持不完整，缓存相关告警可忽略。

### 第三层：推送到 GitHub 后的真实验证（最终标准）

```bash
# 首次推送（见 §5 完整步骤）
git remote add origin git@github.com:<你的用户名>/prep-cex.git
git push -u origin main

# 然后任选其一观察：
# a) 网页：仓库页 → Actions 标签页 → 点最新一次 run
#    通过标准：verify job 全部步骤绿勾，总耗时约 2-4 分钟
# b) 命令行（装了 gh CLI）：
gh run list --limit 1          # 通过标准：✓ main ... success
gh run watch                   # 实时看进度
gh run view --log-failed       # 失败时：只看失败步骤的日志
```

实测状态：本机已完成第一层（actionlint 通过）；第三层待仓库推送到 GitHub 后自然完成——**这正是 CI 设计的目的：每次 push 自动执行**。

### CI 失败速查表

| 现象 | 原因 | 处理 |
|---|---|---|
| `Lockfile does not match` | 改了 package.json 没更新锁文件 | 本地重跑 `pnpm install`，提交 pnpm-lock.yaml |
| setup-node 步骤超时 | GitHub↔npm 网络抖动 | 重跑（Re-run failed jobs） |
| lint 失败但本地过了 | 本地没提交新文件，或 eslint 版本差异 | 本地 `pnpm lint` 确认后再 push |
| prisma generate 失败 | schema 语法错误 | 本地 `prisma validate` 先验 |
| build 时 next 报类型错 | Next 版本升级引入新检查 | 按 CI 日志逐条修，CI 的 TypeScript 就是标准答案 |

## 5. 推送到 GitHub 的步骤（本仓库实际采用：HTTPS + Token）

> 实际执行记录（2026-09-13）：远端 `https://github.com/xl465971060/cex-project.git`，认证用 classic PAT（`repo` 权限），凭证存于 `~/.git-credentials`（权限 600，由 `credential.helper store` 管理），日常 `git push` 免输。

```bash
# 一次性配置（已完成，换新机器时按此重做）：
git config credential.helper store                       # 凭证落盘方式
# 首次 push 时输入用户名 xl465971060 + PAT 作为密码，之后免输；
# 或直接预写 echo "https://<用户名>:<PAT>@github.com" > ~/.git-credentials && chmod 600 ~/.git-credentials
git remote add origin https://github.com/xl465971060/cex-project.git
git push -u origin main
```

PAT 管理与安全：
- 生成入口：GitHub → Settings → Developer settings → Personal access tokens；本仓库推送只需 `repo` 权限（建议以后换 fine-grained token，只授权这一个仓库的 Contents: RW）
- token 一旦贴进过聊天/截图等场所，建议到期后轮换；泄露处理：GitHub 删除该 token 即可，代码不受影响
- SSH 方式（备选）：`ssh-keygen -t ed25519` → 公钥贴到 Settings → SSH and GPG keys（类型必须是 **Authentication Key**）→ remote 换成 `git@github.com:xl465971060/cex-project.git`

推送后验证 CI：网页仓库 → **Actions** 页签，或 `curl -s -H "Authorization: token <PAT>" https://api.github.com/repos/xl465971060/cex-project/actions/runs`（见 §4 第三层）。
